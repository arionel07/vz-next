# Инвентаризация legacy-админки и направление дизайна Next

Дата аудита: 2026-11-05. Это инвентаризация до миграции: CRUD-модули админки пока не переносились.

## Краткий вывод

- В legacy есть административные маршруты `/cp`, `/cp/login`, `/cp/logout` и общий набор экранов в `application/controllers/backend` и `application/views/dashboard`.
- Контроллеры покрывают каталог, заказы, клиентов, маркетинг, контент, главную страницу, магазины, настройки, аналитику и служебные очереди.
- Legacy использует общую проверку сессии. В просмотренных контроллерах не обнаружена проверка ролей и прав на уровне действий. В общей проверке не используются `admins.status` и `admins.adminType`. Мигрировать это поведение как есть нельзя: сначала нужны явная модель доступа и серверная проверка каждого действия.
- В Next найдена Drizzle-схема `admins` и базовые переиспользуемые UI-компоненты, но не найдены admin-маршруты, admin API и административная оболочка.
- Поиск и часть storefront API уже существуют, однако это не заменяет защищённые операции администрирования. Переносить модули следует после стабилизации нужных публичных контрактов и интеграций.

## Legacy: вход и доступ

- Маршруты объявлены в `application/config/routes.php`: `/cp`, `/cp/login`, `/cp/logout`, общие маршруты `/cp/{controller}/{action}/...` и несколько прямых действий панели.
- `BackEndController` читает `admin_id`, `login`, `admin_key` из сессии, находит запись в `admins` и сверяет login и производный ключ.
- Найденная защита общая для вошедших администраторов. Проверок `adminType`, `status`, ролей или гранулярных permissions в просканированных backend-контроллерах нет.
- `Admins` позволяет просматривать/добавлять администраторов, удалять их и менять пароль. Явной матрицы ролей в интерфейсе и контроллерах не найдено.
- В legacy-логе записываются идентификаторы сессии и административный login. В Next следует использовать санитаризированный аудит действий без записи секретов сессии или паролей.

Перед написанием admin CRUD нужно согласовать роли (например, владелец, каталог, контент, заказы, маркетинг, аналитика), права чтения/изменения/удаления и ограничения по опасным действиям. Названия ролей здесь — предложение, а не подтверждённая legacy-модель.

Действия, видимые в контроллерах, включают список, создание/редактирование, удаление, изменение порядка, поиск товаров для связей, обновление статусов и загрузку/удаление изображений. Подробные поля и валидации нужно сверять по форме и модели каждого модуля непосредственно перед его переносом.

## Текущее состояние Next

- Drizzle содержит `admins` и основные таблицы storefront: каталог и варианты, категории/бренды, акции/подарки, заказы/клиенты, статьи, баннеры/слайдеры, магазины, меню, настройки сайта и рулетка.
- В `src/app/api` есть публичные/клиентские области `account`, `auth`, `blog`, `cart`, `contact`, `cookie-consent`, `gift-promotions`, `orders`, `promocode`, `roulette`, `search`, `subscription`.
- До начала этого прохода admin API и маршрутов `/admin` или `/cp` в Next не было. Сейчас добавлены отдельный вход `/admin/login`, защищённый обзор `/admin` и только auth endpoint `/api/admin/auth`; CRUD и API модулей не добавлялись.
- Для входа добавлены `admin_sessions` и `admin_login_attempts`. Парольное поле `admins.password` остаётся в legacy формате SHA-256, чтобы Next не ломал параллельный вход через legacy. Новые сессии хранят только SHA-256 хеш случайного токена; допускаются только аккаунты со `status = 1`.
- Значения `adminType` не трактуются как роли: их смысл в legacy не подтверждён. У админов пока нет ролевого разделения, а операции над данными остаются закрытыми до согласования permissions.
- Уже есть Tailwind и UI-примитивы `button`, `input`, `dialog`, `drawer`, `dropdown-menu`, `table`, `tabs`, `select`, `checkbox`, `radio-group`, `textarea`, `tooltip`. Это база для админки; готового admin shell нет.
- Текущая внешняя интеграционная заметка подтверждает: WorkApp/1С в Next ещё не синхронизируется; Paynet ожидает sandbox-контракт и проверку callback; Meilisearch read-provider существует, но миграция индекса и актуализация требуют проверки. См. `external-integrations-release.md`.

## Направление дизайна админки

- Текущая оболочка: чёрная верхняя строка с мини-логотипом, поиском разделов и аккаунтом; светло-серый sidebar с активной строкой на белом фоне; рабочая область белая. На узком экране sidebar открывается как drawer.
- Поиск с `Ctrl K` фильтрует пункты бокового меню. Обзор показывает приветствие и статические карточки модулей без выдуманных бизнес-показателей. Пункты будущих модулей остаются неактивными до готовности admin API.
- Apple Blue `#007AFF` оставлен для focus/hover и небольших состояний интерфейса; основные поверхности нейтральные, бордовый зарезервирован для ошибки/опасного состояния. Палитра B2C не должна заставлять админку выглядеть как витрина.
- Визуальная форма входа временная и будет пересмотрена после получения нового референса от пользователя.
- Списки строятся вокруг быстрого поиска, фильтров, сортировки, пагинации, выбора строк и подтверждаемых массовых действий. Статусы должны иметь текст, не только цвет.
- Редактор товара: центральная колонка с основными полями, медиа, вариантами, ценой и запасом; боковая колонка с публикацией, категориями, брендом и каналами; сохранение/отмена остаются доступными при прокрутке.
- Заказы: сводные счётчики, фильтры по статусу, таблица со способом оплаты/доставки и суммами; опасные операции требуют серверной проверки и подтверждения.
- Использовать общие Tailwind-примитивы и отдельные admin-композиции. Не менять `b2b.css` и не расширять storefront global CSS ради админки.

## Порядок миграции и блокировки

1. **Основа доступа и оболочка.** Зафиксировать роли и разрешения, безопасную серверную сессию, аудит изменений и защиту admin API. Затем собрать shell и пустые состояния. Не наследовать сессию и отсутствие RBAC из legacy.
2. **Каталог.** Товары, варианты, изображения, категории, бренды и характеристики после проверки контрактов каталога, вариантов, поиска и загрузки изображений.
3. **Контент и витрина.** Статьи/новости, баннеры/слайдеры, меню, подборки и блоки главной после проверки форматов публичных страниц и кеш-инвалидации.
4. **Акции и подарки.** Предложения, подарки, welcome-акции, промокоды и рулетка после стабилизации серверных правил корзины и заказа. Управление в панели не должно обходить те же проверки.
5. **Магазины и настройки.** Адреса/изображения магазинов, доставка и публичные настройки после согласования модели конфигурации и разграничения секретов.
6. **Заказы и клиенты.** Последними, после подтверждения Paynet и WorkApp/1С, правил бонусов, повторов и сверки серверного итога заказа. До этого — только чтение/операции, которые не меняют внешний статус или деньги, если они отдельно одобрены контрактом.
7. **Эксплуатационные экраны.** Аналитика, обратная связь, подписки, импорт и обслуживание поискового индекса — после определения владельца процесса и прав доступа.

### Условия начала каждого модуля

- Публичная сторона уже читает данные через утверждённый контракт.
- Права на чтение и изменение определены, а сервер проверяет их для каждого запроса.
- Согласованы валидация, ошибки, аудит и поведение при конфликте/повторе.
- Для загрузок утверждены ограничения размера/типа, место хранения, удаление и восстановление.
- Для денежных и интеграционных действий определены авторитетный источник состояния и идемпотентность.

**Статус этапа 9:** инвентаризация, миграция сессий, auth endpoint, защищённая оболочка, главная и sidebar готовы. Визуальная форма входа временная. CRUD админ-модулей намеренно не начат до выполнения их API/интеграционных предпосылок и согласования ролей.
